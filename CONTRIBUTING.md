## Development Workflow

We use **Spec-Driven Development (SDD)** - all features start with a specification:

```
1. Specification → 2. Planning → 3. Tasks → 4. Implementation → 5. Testing
```

### SDD Commands

```bash
# 1. Create specification
/sp.specify "Add feature description here"

# 2. Create implementation plan
/sp.plan

# 3. Generate task breakdown
/sp.tasks

# 4. Implement the feature
/sp.implement

# 5. Create pull request
/sp.git.commit_pr
```

## Spec-Driven Development Process

### Phase 1: Specification

Create `specs/<number>-<feature>/spec.md` with:

- **User Stories**: Prioritized (P1, P2, P3) and independently testable
- **Functional Requirements**: Clear, testable requirements (FR-001, FR-002, ...)
- **Success Criteria**: Measurable outcomes (SC-001, SC-002, ...)
- **Edge Cases**: Boundary conditions and error scenarios

**Quality Checklist**:
- [ ] No implementation details (no frameworks, languages, databases)
- [ ] Focused on user value and business needs
- [ ] Written for non-technical stakeholders
- [ ] All functional requirements testable
- [ ] Success criteria measurable and technology-agnostic

### Phase 2: Planning

Create `specs/<number>-<feature>/plan.md` with:

- **Technical Context**: Language, dependencies, platform
- **Constitution Check**: Verify all 7 constitutional principles
- **Project Structure**: Directory layout and file organization
- **Research Decisions**: Technology choices with rationale
- **Data Model**: Entity definitions and relationships
- **API Contracts**: Endpoint specifications (if applicable)

### Phase 3: Task Breakdown

Create `specs/<number>-<feature>/tasks.md` with:

- **Organized by Phase**: Group related tasks
- **Dependency Order**: Specify prerequisites
- **Testable Units**: Each task has clear acceptance criteria
- **Parallel Opportunities**: Mark tasks that can run concurrently

**Task Format**:
```markdown
- [ ] T001 [P] Task description with file path
- [ ] T002 Task description (depends on T001)
```

### Phase 4: Implementation

**CRITICAL**: All code must be generated by Claude Code, no manual coding!

```bash
# Start implementation
/sp.implement

# Claude Code will:
# 1. Read spec, plan, and tasks
# 2. Generate all code files
# 3. Run tests and verify functionality
# 4. Create Prompt History Records (PHR)
```

### Phase 5: Pull Request

## Code Standards

### Constitutional Principles

All code must satisfy the 7 principles in `.specify/memory/constitution.md`:

1. **Spec-First Development**: No code before specification
2. **Deterministic Behavior**: TimeProvider injection for reproducible tests
3. **Explicit State Transitions**: VALID_TRANSITIONS map enforced
4. **Time-Aware Logic**: UTC storage, edge case handling
5. **Data-Driven Recurrence**: RecurrenceRule as dict, not code
6. **Extensibility**: Database/multi-user ready
7. **AI-Readiness**: API-first design for future chatbot integration

### Coding Guidelines

- **No Manual Coding**: All code generated by Claude Code from specs
- **Type Hints**: Use Python type annotations (Python 3.13+)
- **Docstrings**: Document all public functions and classes
- **Error Handling**: Validate inputs, provide clear error messages
- **State Machine**: Use VALID_TRANSITIONS for all state changes
- **Time Injection**: Always use TimeProvider, never `datetime.now()` directly

### File Organization

```

├── models/          # Entities (Task, TaskState, etc.)
├── services/        # Business logic (state_manager, recurrence)
└── storage/         # Data persistence (todo_store)
```

## Testing Requirements

### Running Tests

```bash
cd todo-app

# Comprehensive test suite (41 tests)
python test_all_features.py

# Interactive testing
python cli.py

# Feature demo
python main.py
```

### Test Coverage Requirements

- **Minimum**: 95% test success rate (40/41 tests passing)
- **Categories**:
  - Basic operations (create, read, update, delete)
  - State transitions (all VALID_TRANSITIONS paths)
  - Recurrence patterns (daily, weekly, monthly, edge cases)
  - Time provider (deterministic testing)
  - Validation (input constraints, error handling)

### Writing Tests

```python
# Use TestTimeProvider for deterministic tests
from src.todo_app.services.time_provider import TestTimeProvider
from datetime import datetime, timezone

fixed_time = datetime(2026, 6, 15, 10, 30, 0, tzinfo=timezone.utc)
test_time = TestTimeProvider(fixed_time)

# Test will always use fixed_time, ensuring reproducibility
transition_task_state(task, TaskState.COMPLETED, test_time)
assert task.completed_at == fixed_time
```
