# Implementation Plan: Advanced Todo Features

**Branch**: `1-advanced-features` | **Date**: 2026-01-01 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/1-advanced-features/spec.md`

## Summary

Implement recurring tasks, due dates with time awareness, reminders, and explicit state management for an in-memory console-based Python todo application. Core value: enable habit tracking and time-aware task management through auto-rescheduling recurring tasks, deadline prioritization, and proactive reminders—all while maintaining deterministic behavior for testing and preparing the architecture for future AI chatbot integration (Phases III-V).

**Technical Approach**:
- Data-driven recurrence rules (simplified iCalendar subset) for extensibility and AI parsing
- Time injection pattern (TimeProvider) for deterministic testing of all temporal logic
- Explicit state machine (pending/active/completed/snoozed/cancelled) with transition validation
- Protocol-based notification abstraction for future platform migration (console → browser → mobile)
- In-memory storage with forward-compatible entity design for persistent storage in Phase III+

---

**Language/Version**: Python 3.13
**Primary Dependencies**: Python standard library only (dataclasses, datetime, enum, uuid, argparse)

- Single-user, single-process runtime
- No manual coding (all code generated by Claude Code from specs)

**Scale/Scope**:
- Phase II: Single user, ~100-1000 tasks
- Phase III-V: Multi-user, persistent storage, cloud deployment

## Phase 0: Research & Decisions (✅ Complete)

**Deliverable**: `research.md`

### Architectural Decisions Made

1. **Recurrence Rule Format**: Simplified iCalendar subset (stored as Python dict)
   - Standards-based for future AI parsing
   - No external dependencies (Phase II constraint)
   - Clear upgrade path to RFC 5545 in Phase III+

2. **Time Storage & Injection**: Python datetime (UTC) + TimeProvider dependency injection
   - Constitutional compliance: FR-037 (deterministic testing)
   - Clean separation of system time vs test time

3. **State Management**: Enum + explicit transition map
   - No state machine library (constitutional minimalism)
   - Explicit validation prevents invalid transitions

4. **Reminder Evaluation**: Check on display operations (list/view)
   - Console-only constraint (no background process)
   - UX balance (users see reminders when reviewing tasks)

5. **Data Validation**: Dataclasses with `__post_init__` validation
   - Standard library (no Pydantic dependency)
   - Centralized validation ensures invalid entities cannot exist

6. **Testing Framework**: pytest (acceptable test dependency)
   - Time injection fixtures align with TimeProvider pattern
   - Parameterized tests reduce boilerplate for edge cases

7. **Console Interface**: Interactive prompts + CLI args fallback
   - User-friendly for complex inputs (recurrence rules)
   - Power-user escape hatch (skip prompts with CLI args)

**Constitutional Compliance**: All decisions derive from spec functional requirements and constitutional principles. Zero violations.

## Phase 1: Design & Contracts (✅ Complete)

### Data Model Summary

**5 Entities Defined**:

1. **Task** (10 fields)
   - Core fields: id, title, state, created_at, completed_at
   - Time fields: due_date, due_datetime (UTC)
   - Recurrence fields: recurrence_rule (dict), parent_recurrence_id
   - Snooze field: snooze_until (UTC)
   - Validation: `__post_init__` ensures integrity

2. **TaskState** (Enum)
   - 5 states: PENDING, ACTIVE, COMPLETED, SNOOZED, CANCELLED
   - Explicit transition map: `VALID_TRANSITIONS` dict
   - Terminal states: COMPLETED, CANCELLED

3. **RecurrenceRule** (embedded dict in Task)
   - 6 fields: freq, interval, byday, bymonthday, count, until
   - Validation: frequency-specific rules (weekly requires byday, monthly requires bymonthday)
   - Edge case logic: month boundary adjustments, "LAST" day handling

4. **Reminder** (7 fields)
   - Types: absolute (specific datetime) or relative (offset from due)
   - Delivery tracking: delivered (bool), snoozed_until (datetime)
   - Computed time: calculated from relative offset or absolute time

5. **StateTransitionLog** (6 fields)
   - Audit trail: task_id, timestamp, old_state, new_state, trigger
   - Trigger types: "user_action" or "system_auto"

**Relationships**:
- Task 1:N Reminder
- Task 1:N StateTransitionLog
- Task self-referential (parent_recurrence_id)

**Storage**: `TodoStore` class with in-memory dicts (`tasks`, `reminders`, `transition_logs`)

### CLI Interface Summary

**11 Commands Defined**:

| Command | Purpose | Key Parameters |
| ------- | ------- | -------------- |
| `add` | Create simple task | --title, --due, --due-time |
| `add-recurring` | Create recurring task | --title, --freq, --interval, --days, --monthday, --count, --until |
| `list` | List tasks with filters | --state, --due, --recurring, --all |

| `delete` | Delete task permanently | TASK_ID, --series |

**Error Handling**:
- Clear, actionable messages (e.g., "Error: Invalid date '2026-02-30'. February has 28 or 29 days.")
- Exit codes: 0 (success), 1 (user error), 2 (system error)
- Help text for every command

**Output Formats**:
- Human-readable (default): formatted tables, emoji indicators, color (future)
- JSON (--json flag): structured output for scripting

**Common Pitfalls & Solutions**:
- Naive datetime comparison (solution: always use timezone.utc)
- Forgetting to auto-transition snoozed tasks (solution: call at start of every operation)
- Monthly recurrence on invalid day (solution: fallback to last day of month)
- Reminder firing multiple times (solution: set delivered=True)

## Risks & Mitigations

| Risk | Impact | Likelihood | Mitigation |
| ---- | ------ | ---------- | ---------- |
| **Month boundary edge cases** | High (wrong next occurrence dates) | Medium | Comprehensive unit tests for all month combinations (31→28/29/30, leap years) |
| **DST transition bugs** | Medium (reminder/due time ambiguity) | Low | UTC storage eliminates ambiguity; document local time conversion carefully |
| **State transition violations** | High (data corruption, UX confusion) | Low | Explicit transition map with validation; extensive state machine tests |
| **Reminder duplication** | Medium (UX annoyance) | Medium | Strict `delivered` flag checking; test firing logic thoroughly |
| **Phase I regression** | Critical (breaks existing features) | Medium | Run full Phase I test suite; maintain 100% pass rate |

**Mitigation Strategy**: Test-first approach with edge case coverage. Use time injection for reproducible temporal tests.
